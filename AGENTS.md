# Repository agent instructions

## Codex review loop

Every nontrivial change goes through a pull request into `master` whose final head
has a clean independent Codex review: no P0, P1, or P2 findings. Only trivial
changes limited to documentation, comments, or formatting may skip review.

1. Commit the change and request an independent Codex review of the complete PR
   diff against its base. Record the reviewed head commit.
2. Investigate each finding, fix valid issues in new commits, and run the checks
   appropriate to those fixes. Explain any rejected finding with concrete evidence.
3. Request a fresh Codex review after each head change. Repeat until the final
   head has no unresolved P0–P2 findings; a review of an earlier head does not count.
4. Run PR CI and review in parallel. Merge only when the final head has a clean
   review and required checks pass, and only when merging is authorized.

Report the reviewed head, review outcome, checks performed, and any validation
that remains incomplete. Never claim a review or check passed when it did not run.

## Waiting for CI

When you run in xd and need a pull request's CI result, call xd's `watch_ci`
tool (`mcp__xd__watch_ci`) with the pull request's URL. Do not wait on CI with
`gh run watch`, `gh pr checks --watch`, `sleep` loops or other polling commands,
in the foreground or in a background shell. xd watches the checks, shows them
on a live CI card in the chat, and sends you one report when they finish: what
passed, what failed, and the end of each failed job's log. Carry on with other
work or end your turn meanwhile. After you push again, call `watch_ci` again.
Read a failed job's full log with `gh run view --log-failed` only when the
report's excerpt is not enough.

## Commit and merge authorship

Codex and Claude must never add themselves, each other, or any other AI assistant
as a co-author. Do not add AI `Co-authored-by` trailers or equivalent attribution
when creating or amending commits, preparing PR messages, or merging, squashing,
or rebasing a PR. Inspect the final commit message, including any message generated
by GitHub, and remove AI co-author trailers before committing or merging. Use the
user's configured Git identity and preserve required license notices and attribution.

## UI screenshot proof

Use an isolated Xvfb display for headless Linux screenshot validation. Missing
`DISPLAY`, `WAYLAND_DISPLAY`, or screenshot utilities is a setup task, not by
itself a capture blocker. Start Xvfb and install or configure the capture tools
needed to obtain actual application screenshots.

Every UI change must include before-and-after screenshot proof in the PR
description. Capture the affected UI before editing and again after the change,
using the same viewport, theme, and comparable application state so the difference
is clear. Label both screenshots and cover each affected surface or layout.
Use actual application captures and keep private or sensitive content out of the
images. Do not mark a UI change ready for review or merge until both screenshots
are included; report any capture blockers and incomplete validation explicitly.

## Desktop and mobile parity

Every user-facing feature or behaviour change ships on both the desktop app
(`desktop/`) and the mobile app (`mobile/`). When a change adds or alters a
feature on one client, make the same change on the other in the same PR, or in
a companion PR opened alongside it and merged with it. Match the flow and wording
the other client already uses, adapted to its layout. If the other client cannot
support the feature yet, for example because the host protocol lacks something,
say so in the PR description and open an issue to track the missing side.

## Conventional Commits

Use Conventional Commits for every commit subject and PR title:
`<type>[optional scope][!]: <short description>`. Choose a type that describes the
change, such as `feat`, `fix`, `docs`, `refactor`, `perf`, `test`, `build`, `ci`,
`chore`, `style`, or `revert`; for example, `fix(chat): keep the latest message visible`.
Mark breaking changes with `!` before the colon or a `BREAKING CHANGE:` footer.
When merging a PR, ensure the resulting squash or merge commit subject also follows
this format; inspect and edit any message generated by GitHub before merging.

## Pull request links

Whenever a message to the user mentions a pull request, write it as a Markdown link
to its full URL, such as `[PR #180](https://github.com/restartfu/xd/pull/180)`, so
it can be clicked. A bare `PR #180` or `#180` is not enough, including in progress
updates and final reports.
